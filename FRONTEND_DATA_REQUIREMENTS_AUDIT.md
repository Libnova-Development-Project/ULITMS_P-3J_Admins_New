# ULITMS Frontend Data Requirements Audit

**Scope:** Existing frontend pages and the API/database implementation they currently target.  
**Schema reviewed:** `backend/database/schema.sql`  
**Runtime entry point:** `backend/server.js` loads `backend/src/app.js`; the mounted API routes are in `backend/src/routes/`.  
**Boundary:** Findings and recommendations only. No database or application structures were changed.

## Executive summary

The UI generally uses the SQL user-name fields correctly, and the E-Library can derive session status and duration from `time_in`/`time_out` without storing separate `status` or `duration_mins` fields. The most significant implementation/schema gaps are:

1. Borrowing return requests write and query `pending_return`, which is not in the SQL `borrow_status` enum.
2. The damage-report UI and backend support books (`book_id`, `item_type`), but `damage_reports` has neither column; the backend also writes `books.status = 'damaged'`, which is not in the `book_status` enum.
3. Profile picture and password recovery code reference user columns absent from `users`.
4. Notification endpoints query `library_schema.notifications`, but the reviewed schema does not define that table.
5. Aggregate book counts cannot support copy-specific barcode circulation, condition tracking, or recording good/damaged/lost return outcomes.
6. The System Settings page calls `/api/settings`, which is not mounted.
7. There is no activity-log UI/API, although `activity_logs` exists and backend actions write to it.

These are observed implementation mismatches; they do not imply that every missing concept should be added as a column. For copy-level circulation, user profile images, reset tokens, and settings, the application and database contracts should be agreed before choosing storage.

## 4. Inventory and borrowing interface requirements

### Are aggregate fields sufficient?

`total_copies`, `available_copies`, and title-level `status` support only aggregate availability. They are **not sufficient for the workflow implied by barcode tracking, per-copy damage/loss, or physical return inspection**. The current `borrow_transactions` row refers to `book_id` (a title/catalog row), not a particular physical copy.

The frontend should move toward a title → copy workflow if librarians must identify which physical book was borrowed or returned:

- **Catalog/list view:** retain bibliographic/title fields and show aggregate total/available counts.
- **Book details/inventory view (admin):** list each copy with a stable copy identifier/barcode, condition, circulation state, and acquisition date; allow add/edit/archive per copy.
- **Borrow flow:** select/scan an available copy; the transaction must reference that copy. Keep title metadata linked for search and display.
- **Return flow:** librarian selects the transaction/copy, records `good`, `damaged`, or `lost`, optional notes, and confirms return. A good copy returns to available; damaged goes to an unavailable repair/inspection state; lost remains unavailable and may trigger the appropriate loss/fine workflow.
- **Availability counts:** derive or transactionally maintain title aggregates from copy states. Do not increment availability for damaged/lost copies.
- **Auditability:** preserve the borrower, processed-by librarian, borrowed/due/returned timestamps, assessed condition, and resolution/fine outcome.

Whether to store acquisition date, physical condition, barcode, and copy status as a dedicated copy entity or an equivalent design is a database design decision for Jhon. The frontend requirement is that each physical copy can be uniquely identified and independently circulated/inspected. If copy-level tracking is explicitly out of scope, the UI must clearly present counts as title-level only and avoid implying individual-copy control.

### Existing return workflow

Currently a student submits a return request, the admin confirms it, and backend confirmation marks the borrowing returned, calculates a hard-coded fine of 10 per overdue day, and increments title availability. There is no condition/lost selection and no return notes input. The System Settings page's fine-per-day value is not persisted or used. The required operational decision is whether a librarian must inspect at the counter and distinguish a physically returned good/damaged item from an item reported lost; the existing UI suggests counter confirmation but does not capture those outcomes.

## 5. Frontend validation requirements

Client-side checks improve usability but must not be trusted as the validation boundary. Validate in the API (including authorization and cross-field rules), then enforce durable invariants with PostgreSQL constraints/indexes/transactions.

| Form / data | Frontend validation expected | Backend/database enforcement required |
|---|---|---|
| Login | Identifier and password nonempty; trim identifier; prevent duplicate submits; accessible errors. | Rate limit and authenticate; avoid leaking account state; use safe password comparison. |
| Student registration | Required first/last, student ID, email, password; valid email and agreed student-ID format; password policy; trim strings. | Current validator supports `YYYY-12345` or `YY-B-XXXXX`, validates email, and requires fields; also enforce password policy (current registration path does not call `validatePassword`), unique email/ID and role. |
| Password recovery/reset | Identifier required; PIN has exactly six digits; new password and confirmation match; minimum/policy feedback. | Persist a one-time expiring token safely, rate-limit, invalidate after use, enforce same password policy, and avoid returning the PIN to the client or exposing account existence. |
| Profile edit | First/last/email required; email format; year from agreed values; contact format if supplied; avatar type/size and explicit upload result. | Authorize self/admin, validate allowed fields, uniqueness-check changed email, validate contact/year and image content/size, and reject unsupported updates instead of silently ignoring them. |
| User creation | First/last/email/password required; optional student ID/course/year; valid role; avoid a shared default password; validate ID and year. | Enforce role permissions, unique values, password hash/policy, year range and active/deleted behavior. Current HTML has no explicit required attributes and its JS only checks names/email. |
| Book create/edit | Title/author required; ISBN optional but valid 10/13-digit ISBN if present; category must be selected; copies integer and nonnegative; publication year bounds if collected. | Validate ISBN format/uniqueness, category FK, integer copy counts and reconciliation with active loans. SQL already checks copies nonnegative and `available_copies <= total_copies`; backend create currently treats zero as missing. |
| Borrow request | Select available title/copy; ensure due date is present and consistent with policy; prevent duplicate/repeated submissions. | Verify authenticated borrower, book/copy availability, policy/loan limit, date rules, valid references and atomic inventory update. SQL requires `due_date`; current page computes a 7-day date client-side. |
| Return/confirmation | Confirm correct borrowing/copy; require librarian inspection outcome; notes conditional/optional based on damage/loss. | Enforce valid state transition, authorized librarian, correct target, fine/payment calculation, and atomic inventory/copy update. |
| E-Library session | Unit required and active/available; purpose optional but max 255; prevent duplicate start/end. | Verify active unit, single active session and unit exclusivity transactionally; enforce `time_out >= time_in`. Do not trust client-calculated availability. |
| Equipment | Existing unit required; device name required; valid category; serial number uniqueness; condition from enum; optional brand/model/specifications. | Validate unit FK and activity, non-empty name, category FK, unique serial number and `condition_status`; do not silently coerce invalid condition to `good`. |
| Damage report | Exactly one selectable target; issue type and description required; severity from `low/medium/high/critical`; conditionally request book copy or hardware identifier. | Require reporter authorization, target existence and exactly one valid target; severity enum; description length; log the report and update the target state transactionally. |
| System settings | Validate integers/currency and bounds in UI; reject NaN/empty values; valid email; confirm reset. | Until a real API/storage contract exists, do not report settings saved. Validate policy bounds and ensure borrowing/session behavior consumes persisted settings. |

### Database-level invariants already present

- `users`: unique email/student ID; required first/last/email/password/role; year level 1–6.
- `books`: required title/author/total; total and available copies nonnegative; available cannot exceed total; optional unique ISBN.
- `borrow_transactions`: user/book FKs, required due date/status, nonnegative fine, optional processed-by FK.
- `elibrary_sessions`: required user/unit/time-in and `time_out >= time_in`.
- `peripherals`: required unit/name, unique serial number, enum condition.
- `damage_reports`: enum severity; current schema does not require either a target or description and has no target exclusivity rule.

## 6. Status and deletion conventions

- `book_status`: `available`, `borrowed`, `reserved`, `maintenance`, `lost`.
- `borrow_status`: `borrowed`, `returned`, `overdue`, `lost`; frontend/backend also use unsupported `pending_return`.
- `condition_status`: `good`, `damaged`, `repair_needed`, `missing`; this applies to E-Library units/peripherals, not books.
- Damage report pending/resolved is inferred from resolver/timestamp, rather than a report-status enum.
- User/book/peripheral/unit deletion endpoints soft-delete using `is_deleted`; frontend confirmation copy should say archive/deactivate rather than imply permanent deletion or loss of history.
- The UI should not use title `status` as a substitute for copy condition or infer that any unavailable title is borrowed.
